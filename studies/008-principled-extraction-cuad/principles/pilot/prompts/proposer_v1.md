## System

You are helping derive the implicit annotation conventions of a legal-clause
extraction dataset (CUAD) *from the data alone*. You have not been shown the
annotation guidelines and you must not try to recall them; write down only what
these span pairs license you to say.

Your output is a set of candidate **Principle** records. A principle is a rule
that governs how a hard call gets made — not a description of the data, not a
summary of a clause, not advice about being careful.

## Task definition

Each contract yields exactly one decision per category: either an
**Extraction** (one or more verbatim spans) or an **AbsenceClaim**. There is no
third option and no category may be omitted.

## The evidence

Below is a batch of **contrastive pairs** mined deterministically from the
CUAD training split. Two kinds:

- `cross_label` — two gold-annotated spans with **high surface similarity** but
  **different gold categories**. Whatever distinguishes them is a convention.
- `present_absent` — a gold span of category C, matched against a passage from
  a different contract in which C is annotated **absent** (`is_impossible`).
  Either the annotators declined to mark that passage, or the convention draws
  the category tighter than the surface language does.

## What you must produce

A YAML list of candidate principles. Each record, exactly these keys:

```yaml
- id: dNN                       # d01, d02, ... assigned in order
  statement: >                  # the rule, ONE sentence, imperative or declarative
  trigger_guidance: >           # when a reader should consider it
  type: constraint | procedure | preference | disambiguation | absence
  scope: []                     # category names it can touch; [] means global
  provenance: data_mined
  evidence: [pair-NNNN, ...]    # the pair ids you read it off. REQUIRED.
  n_supporting_pairs: 3         # len(evidence)
  checker_sketch: >             # REQUIRED. How a program would compute
                                # gold_applicability from (instance,
                                # gold_annotations) — i.e. decide whether this
                                # principle APPLIES to a given decision. Name
                                # the concrete inputs and the test.
  defect_argument: >            # why this is a convention and not gold noise
```

## Hard constraints — a candidate that fails any of these must not be emitted

**1. Feasible checker.** `checker_sketch` must describe a computation over the
instance text and the gold annotations that a competent engineer could
implement in an afternoon: lexicon matches, offset comparisons, gold
present/absent flags, span-length tests, regexes. "A lawyer decides" is not a
checker. If you cannot write one, drop the principle.

**2. Not already enforced by the output schema.** The harness guarantees
exactly one decision per category and validates the structure before anything
is scored. A principle like "emit a decision for every category" or "cite at
least one principle" would show 100% compliance in every experimental condition
by construction and measure nothing. **Screening test: describe, to yourself, a
schema-valid output that VIOLATES the principle. If you cannot, drop it.**

**3. Convention, not defect.** This gold contains real annotation errors:
plain mislabels, spans captured by neighbourhood rather than content, and spans
split around embedded OCR/SEC page furniture. A "principle" read off a single
pair where one side is simply wrong is noise dressed as business logic.
**Require support from multiple pairs, ideally spanning more than one
contract**, and say in `defect_argument` why the pattern is a convention rather
than an error. If a pair looks to you like a mislabel, say so — but do not turn
it into a principle. One-pair candidates are permitted only when the pair is a
near-verbatim contrast within a single contract (the strongest possible minimal
pair), and you must say so explicitly.

## Further instructions

- **Quality over count.** Four defensible principles beat twelve plausible
  ones. Do not pad.
- Prefer principles that would change a decision. A rule nobody could violate
  is not worth measuring.
- Some of the pairs in this batch are **mining noise** — two spans that share
  boilerplate and nothing else. Say which, in a trailing `notes:` block. Do not
  build principles on them.
- Principle statements must be portable in form: they may name CUAD categories
  in `scope`, but the `statement` should read as a rule about how a decision is
  made, not as a CUAD-specific implementation note.
- Output **only** the YAML document. No preamble, no explanation outside it.
