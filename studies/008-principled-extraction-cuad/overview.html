1The question and the three conditions

An agent performs a task governed by an explicit set of principles (“business logic”). Phase 1 asks whether giving it those principles helps, and whether making it cite them helps further.

The study question, verbatim from study.md: does requiring principle citation in structured agent outputs improve task performance? The working framing carried over from the reference plan is making process supervision verifiable by constraining the process vocabulary. Phase 1 compares three inference-time conditions on CUAD clause extraction; Phase 2 (unscheduled) would fine-tune on Tinker with a composite reward over answer correctness and citation correctness.

Three ingredients, only one of which is manipulated

The conceptual frame that makes the comparison clean is the separation of three things that are easy to conflate:

  • Task definition — decision kinds, targets, and one-line target definitions. Present in all conditions. This is decision D-1: an alternative bare “C0” with neither task definition nor principles was rejected, because without the task definition the task is undefined and C1 stops being a fair baseline for “does business logic help”.
  • Principles — the manipulated variable. The explicit business logic governing the hard calls, supplied as data (never hardcoded) from the locked principle set.
  • Citation — the requirement. Whether each emitted decision must name the principle ids that governed it.

Conditions differ only in these three switches, assembled from a single source of truth in the harness:

ConditionTask definitionPrinciples Citation requiredWhat it isolates
C1 baseline yesnono Task performance with the task defined but no business logic supplied.
C2 principles yesyesno The effect of provision: principles are in the prompt, nothing is required of the output.
C3 cite yesyesyes The effect of the citation requirement, over and above provision.
A fourth axis, deliberately not a condition. Whether the principles_cited field is present in the C1/C2 output schema is a separate axis, not a condition. It is open, and is resolved from data by pilot P0 (inv 004) at gate G3. The two competing risks are contamination (models populate a present-but-instructed-empty field, so C1/C2 stop being clean no-citation conditions) and confound (a field-absent schema changes format burden across conditions, so any C3 effect is partly a schema effect). There is no free option.

2The five hypotheses, and who produces the evidence

Verbatim from the reference plan (v2, 2026-08-15), each annotated with the workstream that would supply its evidence.

H1

Performance. Providing principles improves task success; requiring citation improves it further by forcing deliberation at decision points.

Evidence from inv 005 (Phase 1 condition grid) — this is the investigation that answers H1. Reads trial-level rows.

H2

Generalizability (Phase 2). Composite-reward fine-tuning generalizes better than answer-only reward, including to held-out / edited principles.

Evidence from Phase 2 only — not scheduled Phase 2 opens after inv 005 returns results. The β=0 ablation is the key comparison.

H3

Small-model leverage. Explicit principles + citation lets small models match or beat frontier models on business-logic-dominated tasks.

Evidence from inv 005’s model axis (~8B open, ~32B open, one frontier API model — exact picks open), extended by Phase 2’s post-FT size grid.

H4

Diagnostics. Citation errors form an interpretable confusion structure over principles, enabling maintenance of the principle set itself.

Evidence from inv 005’s confusion matrix over principle ids, which must be derivable from decisions.jsonl alone. Depends on WS2 (the principle set, including 3–5 deliberately rare principles so the structure isn’t dominated by a few high-frequency rules) and WS3 (gold applicability).

H5

Failure characterization. System failure modes are measurable and attributable, notably small-model degradation with contract length.

Evidence from inv 005, length-stratified, resting on WS1’s length distribution and on the standing rule that infeasible_at_length is a reported outcome and never a dropped row.

What WS1 has already delivered complete

WS1 is the one unit that has run. It is reported here because everything downstream is sized against it — not as evidence for any hypothesis.

  • Splits are built and frozen. Seed 20260815. Holdout = the 102 official test contracts; dev = 40 drawn from the 408 official-train contracts, stratified on length_bucket × positive-count tercile; FT-train = the remaining 368. Disjoint, union 510, written to files and read back by id, never recomputed.
  • Source of record is CUADv1.json, all 510 contracts and all 41 categories; test.json supplies only the holdout titles. The manifest carries all 41 categories so a subset change at G2 is a config edit, not a dataset rebuild.
  • Provisional 12-category subset is picked, including the Savelka trio; selection criteria are in scripts/config/category_subset.yaml, which is the source of truth. Still provisional until inv 002.
  • Deterministic rebuild via scripts/rebuild.sh; a second run reproduces every output byte-identically apart from built_at. The loader scripts/cuad_dataset.py satisfies env-interface (a) and (d).
WS1 corrected the reference length distribution, and this propagates. The character figure reproduces exactly (holdout median 25,657 chars vs the stated ~25.7k), but the reference token figures do not: they were produced by a 4-chars-per-token heuristic. CUAD contract text runs at 4.70 chars/token under the pinned Qwen/Qwen3-8B tokenizer, so the heuristic overstates length by ~18%. Holdout, tokenizer-derived: median 5,440 tokens, 37 contracts ≤4k, 66 ≤8k, 83 ≤16k, max 64,640 — against the reference’s ~6.4k / 27 / 63 / 79 / ~75k. The tokenizer column is carried forward and the reference token figures should be retired. Every downstream use of “27 contracts ≤4k tokens”, including feasibility planning against an 8B context window, needs re-deriving.
Open calls raised by WS1, flagged for G1. Dev is systematically longer than holdout (median 8,248 vs 5,440 tokens) — not a sampling bug, but a consequence of stratifying dev to mirror its own pool rather than holdout’s length profile; flagged as a deliberate choice needing a decision. The two rare categories are near-degenerate for extraction on holdout (Source Code Escrow: 1 positive; Most Favored Nation: 3), excellent for absence calibration but giving almost no extraction signal — keeping both may be redundant. train_separate_questions.json is fetched but unused. contract_id is the CUAD title string and is not filesystem-safe. The tokenizer is pinned by model id, not file digest.

The four gates

  • G1 (after WS1) — category subset provisional, split files frozen and seeded. Nothing downstream may resample splits.
  • G2 (after WS2) — Tyler curates the principle set. Nothing enters the scored set without a feasible checker/labeling plan. Locked before WS3 implements checkers.
  • G3 (after WS4) — the schema decision, made from data per the P0 decision rule, written into plans/decisions.md.
  • G4 (before inv 005 touches holdout) — the official test split (102 contracts) is untouched until this gate. Dev-set iteration only before it.
Sequencing risk called out in the plan. WS5’s prompt templates encode the principle set’s shape and WS3’s checkers encode its content. If G2 slips, both stall. The mitigation is to have WS5 take the principle set as data (never hardcoded) and to have WS2 lock a small provisional set early enough to unblock P0, accepting that the locked set may grow before inv 005. Changing the locked set after inv 003 has labeled against it means re-labeling — the lock is expensive.

Two backends, tested separately

Track B’s deliverable is the interface; two working implementations are the proof it generalizes. Both must work before the harness is considered done, and they must be tested separately because they exercise different failure modes: qwen3.5:8b via ollama on the desktop RTX 3080 (watch the format/JSON-schema path and the context window actually configured on the served model — a silently-truncating num_ctx would corrupt every infeasible_at_length determination in the study) and inkling-small via Tinker (watch availability and real context window, still open, and whether structured output comes from a schema-constrained decode or from prompt-plus-parse, since the repair-policy accounting differs). A third backend — the frontier API arm — is expected but not yet chosen.

4The measurement chain, and why it is a chain

The study does not just compare endpoint scores across conditions. It reports a mediation path: principles change compliance, and compliance is what should change success.

Figure 2 — Why compliance sits in the middle. Compliance is checked independently of citation and is measured in all conditions, including C1 where no principles were supplied at all. That is what makes it a mediation variable rather than a manipulation check: a model can satisfy a principle it was never shown, and the study needs to know how often. The citation effect is defined as Δcompliance beyond provision, which is only computable because C2 exists as a middle rung.

The three metric families, per the harness metrics module:

  • Answer — token-level span F1 (Jaccard-style, per the LLM-era CUAD literature) + exact category match + absence accuracy. Reported per-category and length-stratified.
  • Compliance — checker pass-rate over applicable principles. All conditions.
  • Citation (C3 only) — per-decision precision / recall / F1 of cited ids against the scope-relevant slice of gold applicability, plus a confusion matrix over principle ids (this feeds H4).

Length stratification is a property of the metrics module, not of individual analyses — every primary metric comes out bucketed. Buckets are token-based (≤4k / 4k–8k / 8k–16k / >16k). The plan’s reference distribution for the official test set was median ~25.7k chars ≈ 6.4k tokens with 27 contracts ≤4k tokens, 63 ≤8k, 79 ≤16k, max ~75k; WS1 reproduced the character figure and superseded the token figures (see §3) with median 5,440 tokens, 37 ≤4k, 66 ≤8k, 83 ≤16k, max 64,640.

Two structural commitments that make the chain measurable.
(1) No LLM judge anywhere in the scoring path (D-4) — every Phase-1 and Phase-2 metric is programmatic or hand-labeled. A judge in the loop would contaminate the Phase-2 reward story, and the point is programmatic verifiability of the process.
(2) Gold applicability is held outside the prompt — a checker (instance, gold_annotations) -> bool, per decision point where the principle is decision-scoped. A principle without a feasible checker or labeling plan does not enter the scored set.
Contamination caveat travels with every result table. CUAD is public and present in pretraining corpora. Condition comparisons are valid under shared contamination; absolute numbers are not leaderboard-comparable.

5The two-level results store

Two append-only JSONL files per run, both in git (D-10). The split is not tidiness — it is the difference between quantities that exist per trial and quantities that exist per decision.

Trial-level rows answer “did this trial run, and how well did it do overall” — H1, H5, parse failures, feasibility. Decision-level rows are what citation P/R/F1, the H4 confusion matrix, and Phase-2 reward extraction actually consume. Those are per-decision quantities, and flattening them into the trial row would destroy them. The rejected alternative was a single trial row with nested decisions: nesting makes those computations awkward and impossible to stream.

Invariants that the two-level shape exists to protect

  • gold_applicable is the scope-relevant slice for this decision. Otherwise citation precision is unfair to any model that doesn’t cite globally-scoped principles everywhere.
  • Every category not extracted produces an absence decision row. Absence is an explicit decision, never an empty slot.
  • Rows are written for non-ok trials too, with score fields null. Dropping them would silently bias H5.
  • Both files are append-only and rebuildable from raw responses + the principle set version.
  • The H4 confusion matrix is built by pairing fp against fn within a decision row — “cited p03 where p11 applied” — so it must be derivable from decisions.jsonl alone.

Raw model responses stay local per the study’s repository policy; response_sha256 is the join key back to them. What goes in git is the deterministic build script, the instance manifest (no full contract text), the principle set and checkers, the per-trial scored records, prompt templates, config, and figures with their source scripts. Rationale: H5 claims are length-stratified and must be auditable from the repo alone, which the scored records give us.

8Phase 2 — Tinker fine-tuning not scheduled

Carried forward unchanged from the reference plan and recorded only so Phase-1 design choices stay compatible with it. It opens only after inv 005 returns Phase-1 results.

Shape

  1. SFT bootstrap — deliberative-alignment pattern: principles in prompt → generate → filter by grader → chat-SFT recipe.
  2. RL — composite reward α·answer + β·citation_F1 via a custom cookbook Env, with rl_basic.py’s loop as the reference implementation. The β=0 ablation is the key comparison. F1, not recall, so cite-everything doesn’t win. Fully programmatic reward; no judge.
  3. Faithfulness check — ablate a cited principle from the prompt-time set and verify behavior changes (TTS-adjacent).

Headline experiments

  • Composite vs answer-only reward at matched compute.
  • OOD: held-out and edited principles.
  • Post-FT size grid vs frontier (H3).
  • Rule-ablation faithfulness.

FT training data comes from the official-train remainder only. The official test split stays untouched until final results.

Two obligations this places on Phase 1

  • The results store must retain enough per-decision structure to build SFT targets and compute citation F1 as a reward, not just as an analysis metric. (This is part of why D-10 splits the store.)
  • The principle set must support “held-out” and “edited” variants — so Principle records need stable ids, and the prompt assembler needs to take a principle subset as a parameter.
