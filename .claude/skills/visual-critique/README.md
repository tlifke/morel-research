# visual-critique — what to pass

`SKILL.md` tells the agent what to do. This tells you what it needs from you.

## The three things you must supply

| Input | Why it matters | Example |
|---|---|---|
| **Target** | What to render. A file path or a URL. | `./view_fixed.html`, `http://localhost:3000/runs/42` |
| **Goal** | One sentence on what the page is *for*. This is the rubric — there is no config file. Without it you get generic UI advice. | "A researcher should be able to see each pipeline step and its inputs and outputs." |
| **Source** | What code produces the page, so findings point somewhere actionable. | "Generated by `build_view.py`", "Next.js app under `src/app`" |

Everything else has a working default.

## Optional, in rough order of usefulness

- **Hidden states.** If content is behind interaction — collapsed `<details>`, tabs,
  an overlay — say so. Critiquing a page of closed bars tells you nothing. The
  `/critique` template asks for this automatically.
- **Opinionatedness.** Same run, different wording: *"list only what is
  objectively broken"* vs *"critique this as a harsh design critic"*.
- **Critics.** Defaults to `Qwen/Qwen3.8-27B` + `thinkingmachines/Inkling-Small`.
  Narrow to one for a fast/cheap pass. `deepseek-ai/DeepSeek-V4-Pro` is text-only
  and is auto-skipped.
- **Viewport.** Default 1280px wide. Pass a narrower width to check responsive
  behaviour.
- **Wait.** Slow dev servers need `--wait <ms>` before capture.

## Three ways to run it

**Prompt template** (interactive Pi) — fills in the inputs and hardcodes the steps
a weak model tends to skip. Note this is a *client-side text macro*: Pi expands it
in the editor and sends the resulting prose, so **the model never sees the name
`/critique`** and cannot tell you anything about it. Only `visual-critique` (the
skill) is visible to the model. They are the same feature, one is just the front
door:

```
/critique ./view_fixed.html a researcher should see each pipeline step and its
inputs/outputs — generated by build_view.py
```

**Skill directly:**

```
/skill:visual-critique Critique ./view_fixed.html. Goal: ... It is generated by
build_view.py. Capture both the default state and an expanded state.
```

**By hand,** when you want exact control over what gets captured:

```bash
uv run .claude/skills/screenshot-page/capture.py \
  --target ./view_fixed.html --out /tmp/crit --label expanded \
  --js "document.querySelectorAll('details').forEach(d=>d.open=true)"
```

then pass the printed paths to `survey_llms` yourself. Re-critiquing the same
PNGs with a different question needs no re-render.

## Mistakes that waste a run

- **Omitting the goal.** You get generic advice about spacing and colour.
- **Not capturing the interacted state.** The worst defects usually hide inside
  collapsed sections. Inkling-Small skips this unless told; the template forces it.
- **Sending every tile in one call.** These are reasoning models sharing one token
  budget between thinking and answering; several images at once makes them ramble
  and run out before answering. One image per call.
- **Trusting a finding you cannot see.** At low resolution or on crowded pages
  these models invent plausible detail — CSS class names, misquoted footers. If you
  cannot point at it in the PNG, drop it.

## Reading the output

Findings are plain text, deduped across critics. Watch stderr from `capture.py`:
`content overflows horizontally` means the page is wider than the viewport, which
is a real defect and not a capture artifact — the capture deliberately shows what a
reader sees rather than zooming out to fit.

One critic is not enough. On this repo's own test page, one missed a wrongly
nested section tree that the other caught immediately.
