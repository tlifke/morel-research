Is structured output actually enforced on the Tinker OAI endpoint?

Study 008 · endpoint https://tinker.thinkingmachines.dev/services/tinker-prod/oai/api/v1 · all payloads below are live responses captured 2026-08-15T12:23:12-0500 · reproduce with harness/scripts/probe_structured_output.py

Verdict

ALL THREE MODELS — the endpointGENUINELY UNENFORCED
Not a bug on our side. No configuration of the Tinker OAI endpoint constrains the decode. response_format (both json_object and json_schema, with and without strict/name), vLLM guided_json, guided_decoding_backend, structured_outputs, nvext and extra_body nesting are all accepted with HTTP 200 and all produce output statistically indistinguishable from sending no parameter at all (the none control matches every mechanism, in both Part 2 and Part 3). Two invalid controls are also accepted, proving the field is never parsed. The native SDK has no such surface either. Do not send these parameters expecting effect.
Qwen/Qwen3.5-4Bunenforced, but conforms well when prompted with the schema
20/20 strictly-parseable JSON and 19/20 schema-valid + coverage-valid under the study's real prompt on a short contract. Under an adversarial prompt that invites prose, 8–10/10 fenced and 0/10 strictly parseable — identical to the no-parameter control. Conformance is a property of the prompt, not of any server-side enforcement. Its distinctive failure is reasoning overflow: with a fence-inviting prompt it returned empty content in 1–4 of 10 samples per mechanism.
Qwen/Qwen3.5-9Bunenforced, but conforms well when prompted with the schema
20/20 strictly-parseable, schema-valid and coverage-valid under the study's real prompt on a short contract. Under the adversarial prompt, 9–10/10 fenced and 0/10 strictly parseable, again matching the control exactly. Never emitted a tool call under any tool_choice, on either the OpenAI- or the Anthropic-compatible endpoint.
thinkingmachines/Inkling-Smallunenforced — the previous "json_object honored" note is WRONG
20/20 strictly-parseable, schema-valid and coverage-valid under the study's real prompt — the best of the three — but that is voluntary compliance, not enforcement. Under the adversarial prompt it emitted a markdown fence on 10/10 samples with response_format: {"type": "json_object"} set, identical to the control. The structured_output: "json_object" entry in TINKER_MODEL_FACTS and the matching claim in plans/component-contracts.md are falsified and must be corrected to prompt_only. It is the only model that emits tool calls at all (17/20 under a forced named tool), but even then tool_choice is not honoured — it declines 3 times in 20.
Answering the framing question directly: this is NOT a misconfiguration. Fourteen distinct request shapes — every OpenAI and vLLM structured-output knob we could name — were sent live to the endpoint. All fourteen returned HTTP 200, including two deliberately invalid controls that any server parsing response_format would have rejected with a 400. The endpoint does validate model (400 on an unknown one) and does honour temperature, so requests are genuinely parsed — the structured-output parameters specifically are dropped before reaching anything that could act on them. Three independent lines of evidence agree, below: live probes, the published docs, and Thinking Machines' own cookbook proxy, which rejects response_format with a clean 400 rather than pretending to honour it.
And the finding that changes the stakes. “Not enforced” turned out not to mean “models cannot conform.” Under the study's real prompt — which embeds the JSON Schema verbatim — all three models produced strictly parseable JSON on 20/20 samples and schema-valid, coverage-valid output on 19–20/20. The catastrophic-looking rates in the earlier assessment came from prompts that either omitted the schema or actively invited prose. Both effects are shown separately below so you can see which is which. Read the limitation in Part 3 before quoting these rates: they are measured on one short synthetic contract, not on real CUAD documents.

A server that parsed response_format would reject {"type": "not_a_real_format"} and would reject {"type": "json_schema"} sent with no json_schema body. Both are accepted with HTTP 200 and a normal completion. Since an unknown model does produce a 400 ({"detail":"Sampling is not supported for not/a-real-model."}), the request body is being parsed; response_format is simply not part of what it parses.

No /openapi.json, no /docs, no /responses. /models lists only the caller's own fine-tuned sampler weights, not the base models — so the base model ids the study uses are not discoverable from the endpoint, and there is no served capability document to consult. The 400 wording on an unknown model is not vLLM's; this is a bespoke shim in front of Tinker's sampler, which is the most likely reason vLLM's guided_json does nothing.

What the documentation says

Independently checked against the published docs and source (fetched 2026-08-15). Relay these as claims to spot-check, not as things I ran:

  • The OpenAI-compatibility page documents only model, messages, prompt, max_tokens, temperature, top_p, separate_reasoning and reasoning_effort. It never mentions response_format, json_schema, json_object, guided_json, logit_bias, or any grammar feature — and it never states how unknown parameters are handled. Our probe answers that omission: silently ignored.
  • The native SDK's SamplingParams has exactly six fields: max_tokens, seed, stop, temperature, top_k, top_p. There is no structured-output, grammar, guided-decoding, logit-bias, or logit-processor surface anywhere in the SDK. So the capability does not exist one layer down either — the shim is not hiding it.
  • Thinking Machines' own cookbook ships a self-hosted OpenAI-compatible proxy whose _UNSUPPORTED_OPENAI_KEYS includes response_format, with a test asserting it returns HTTP 400, and a README line: “Anything else that changes semantics is rejected with a clean 400 rather than silently ignored.” Their own stack has nothing to implement response_format with. The hosted shim differs only in being less honest about it.
  • separate_reasoning defaults to true (changed from false in June 2026), which is why reasoning_content arrives split out of content without us asking. Worth setting explicitly in the backend so a future default flip cannot silently move reasoning text back into content.
  • No recipe in the cookbook does enforced structured output. Their mechanism is: render the schema into the prompt, sample free text, parse afterwards, and report a MALFORMED termination on failure. That is exactly what this harness already does.

Tinker also serves an Anthropic-compatible endpoint at /anthropic/api/v1/messages (undocumented on the OAI page; found by probing) which accepts tools with an input_schema and a tool_choice. Part 4 — the coverage invariant, separately

The study's invariant is: the union of extractions and absent covers each of the 12 target categories exactly once. The claim under test is that even a perfect schema-constrained decode could not enforce this. That claim is confirmed for the output shape we currently use, and refutable by changing the shape — both halves matter.

Confirmed: not expressible over two arrays

JSON Schema (2020-12, and every dialect a decode backend implements) has no operator that relates the contents of one array to the contents of a sibling array. Specifically:

  • uniqueItems is scoped to a single array and compares whole items, not a projected field. It cannot say “no two items share a category”, and it certainly cannot span extractions and absent.
  • minItems/maxItems constrain each array's length independently. There is no way to constrain the sum of two array lengths to 12.
  • enum on category restricts the vocabulary — the only part of the invariant a schema does capture. It gives “every category named is one of the 12”; it gives nothing about at least once or at most once.
  • There is no $data reference, no cardinality quantifier, and no cross-branch counting construct in the standard. ($data is an Ajv extension, not JSON Schema, and no constrained-decode grammar compiler supports it.)

The one loophole is brute enumeration: a oneOf listing every legal ordered partition of 12 distinct categories into two sequences. That is 212 × k!(12−k)! summed over k, i.e. ≈2 × 1012 branches. It is not a schema anyone can compile into a decoding grammar. Treat the invariant as inexpressible in this shape.

Refuted, in the useful direction: reshape and it becomes structural

The invariant is a property of the shape, not of JSON Schema's power. Replace the two lists with one object keyed by category:

{
  "type": "object",
  "properties": {
    "governing_law":   {"$ref": "#/$defs/decision"},
    "expiration_date": {"$ref": "#/$defs/decision"},
    ... all 12 ...
  },
  "required": [ ...all 12 category ids... ],
  "additionalProperties": false,
  "$defs": {
    "decision": {"oneOf": [
      {"properties": {"present": {"const": true},  "spans": {"type":"array","minItems":1},
                      "principles_cited": {"type":"array"}},
       "required": ["present","spans","principles_cited"], "additionalProperties": false},
      {"properties": {"present": {"const": false}, "principles_cited": {"type":"array"}},
       "required": ["present","principles_cited"], "additionalProperties": false}
    ]}
  }
}

Here required gives at least once, additionalProperties: false gives no strangers, and object-key uniqueness gives at most once for free. Coverage becomes an ordinary structural constraint that any grammar-based decoder enforces. So the honest statement is not “JSON Schema cannot express coverage” but “coverage is not expressible over a two-list shape, and is trivially expressible over a per-category-key shape”.

This is a real design option for the study, not a rhetorical point — but it buys nothing on Tinker, where no schema is enforced at all. It would matter the moment the ollama arm (which does have constrained decode) returns, and it would come at a cost: the per-key shape makes the field-absent principles_cited variant harder to strip cleanly, and it changes the prompt, so it is not a free swap mid-study.

How often is coverage actually violated?

Measured in Part 3, independently of JSON and schema validity. On the short synthetic contract, under the study's real prompt, coverage held on 19/20, 20/20 and 20/20 samples for the 4B, 9B and inkling-small respectively; among samples that were schema-valid, coverage was violated zero times. So on an easy instance the invariant is not the binding constraint. Two things stop this from being reassuring:

  • The earlier probe run — same models, same settings, but a prompt that described the output in prose instead of embedding the schema — produced coverage failures on 13/20 (9B) and 5/20 (inkling) samples, always missing categories, never duplicated. The failure mode is silent under-enumeration: the model reports the categories it found and stops. That is precisely the failure that gets worse as documents get longer and the category list gets further from the answer.
  • Coverage is the one failure class that repair cannot be counted on to fix cheaply, because the fix requires re-reading the document for the categories that were skipped, not reformatting what was already produced.

semantically wrong extractions / hallucinated spans No. Out of scope for any schema. Irreducible — and it is the actual object of study.

What this means for the study

  • The line in plans/component-contracts.md saying json_object is “honored” for inkling-small is falsified. structured_output must read prompt_only for all three Tinker arms, inkling included.
  • The doc's stronger claim — “json_schema is unenforced everywhere and on the 4B it burns the whole budget on reasoning and returns empty content” — is half right. Unenforced: confirmed. Empty content on the 4B: real, but it is a prompt-dependent effect (1–4/10 with a fence-inviting prompt, 0/20 with the study's real schema-embedding prompt), not a property of the model. Attributing it to json_schema was a mis-attribution.
  • Because no arm on Tinker gets constrained decode, P0's field-absent leakage measurement is clean across all three arms — that conclusion survives, and now rests on measurement of all three models rather than inference about two.
  • Parse-and-repair is not a fallback here, it is the mechanism. Repair-rate differences between models are a first-class result, and the first-attempt/final double-scoring already specified is the right treatment. But note the measured repair demand on an easy instance is near zero for all three models — the “inkling 0 repairs, both Qwen arms routinely 1–2” asymmetry recorded in the contracts doc is not reproduced here and should be re-measured on real CUAD instances before it is relied on.
  • Sending response_format at all is harmless but misleading: it makes trial rows look as though enforcement was requested. Drop it, or record it explicitly as inert.
  • The single largest open risk is length. Every conformance number on this page comes from a ~350-word document. Re-run the Part 3 measurement on real CUAD instances stratified by length bucket before treating any of these rates as the study's.
