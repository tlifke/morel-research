# visual-critique

An agent that builds a UI gets back an exit code, not a look at the page. Every
layout defect — clipped text, overlapping elements, wrong nesting, a stylesheet
that failed to load — is invisible to it. This skill closes that gap: render to
pixels, ask vision models, hand back concrete findings.

Scope is **feedback only**. Applying the fixes is a separate job.

## 1. Render it

```bash
uv run .claude/skills/screenshot-page/capture.py \
  --target <url-or-path> --out <dir> --label collapsed
```

`--target` takes a URL (dev server: React, Next.js, a Plotly app) or a local
file path (static HTML, an exported figure). Output PNG paths are printed to
stdout.

If the page hides content behind interaction, capture a second state:

```bash
uv run .claude/skills/screenshot-page/capture.py \
  --target <url-or-path> --out <dir> --label expanded \
  --js "document.querySelectorAll('details').forEach(d=>d.open=true)"
```

`--js` runs before capture — use it to expand sections, open a tab, dismiss a
modal. **Always capture the interacted state if content is collapsed by
default**, or you are critiquing a stack of closed bars.

Useful flags: `--width` (viewport, default 1280), `--wait` (ms, for slow apps),
`--tile` (slice height, default 2000), `--max-tiles` (default 6).

Watch stderr. `content overflows horizontally` means the page is wider than the
viewport — that is itself a defect worth reporting, and the capture deliberately
shows what a reader sees rather than zooming out to fit.

## 2. Ask the critics

```
survey_llms(
  models=["Qwen/Qwen3.8-27B", "thinkingmachines/Inkling-Small"],
  imagePaths=["<dir>/expanded-01.png"],
  maxTokens=4000,
  question="<goal sentence>. <what the source is>. List the specific things
            that are broken or unreadable. For each say what you see and what
            to change in the source. Only list what you can actually see.
            Answer as a short numbered list."
)
```

**The question is the rubric.** There is no rubric file. Say what the page is
*for* ("a researcher should be able to see each pipeline step and its inputs and
outputs") and name the source ("this is a Next.js app under `src/app`", "this
page is generated by `build_view.py`") so findings point somewhere actionable.
Dial opinionatedness by wording: *"list only what is objectively broken"* versus
*"critique this as a harsh design critic"*.

Two practical rules:

- **Send one page-view per call**, not every tile at once. Many images in one
  call pushes these models into long rambling reasoning and they run out of
  budget before answering. Loop over tiles and merge.
- **Use two critics.** On this repo's own test page one critic missed the worst
  defect — a wrongly nested section tree — that the other caught immediately.
  `deepseek-ai/DeepSeek-V4-Pro` is text-only and is auto-skipped.

Give it room: `maxTokens` of at least 4000. These are reasoning models and
reasoning shares the budget with the answer.

## 3. Merge and hand off

The critics overlap heavily; the union is short. Drop anything not visible in
the capture — low-resolution or crowded input makes these models confabulate
plausible-sounding details (invented CSS class names, misquoted footers). If a
finding cannot be pointed at in the PNG, discard it.

Then hand off per the caller's `check_in` preference:

- `every` (default) — show the merged findings to the human before anyone acts.
- `after:N` — hand straight to the applier for N rounds, then show.
- `on_request` — hand off directly; surface when the agent asks.

Start at `every` until the findings have proven trustworthy on the artifact at
hand.

## Re-checking

After fixes land, re-run steps 1–2 and compare. **If a finding reappears after
being "fixed", stop and tell the human** — an applier oscillating between two
bad states is the likeliest failure mode and is invisible from inside the loop.
